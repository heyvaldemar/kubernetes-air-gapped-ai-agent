# 23. The boundary on AKS: a network isolated cluster, no name lookup out, and one delete

- Status: accepted for phase 1, 2026-10-30; weekly from 3 November 2026; on Pay-As-You-Go from 10 November 2026; phase 2, the agent, accepted by hand on 13 November 2026 and put on the schedule on 14 November 2026, its first scheduled run due 17 November 2026
- Date: 2026-10-30

## Context

ADR 18 made the boundary on a real AWS account and ADR 22 on a real Google Cloud project, each tried from inside. A buyer on Azure asks the same questions, and four answers differ there.

- **A VM was given a way out nobody asked for.** On Azure a virtual network has no internet gateway to leave out, but a VM in a subnet with no explicit way out was long given one anyway: default outbound access, an address Azure picks. Microsoft is retiring it, and each subnet says whether it has it (`defaultOutboundAccess`).
- **DNS is the same way out.** Every VM resolves through Azure's DNS at 168.63.129.16, the host's own address, which answers any name on the internet. A network security group does not govern it. A workload with no route out can still put data into the names it looks up, as on AWS and Google Cloud.
- **AKS fetches its own parts from the internet.** A node pulls AKS's images from `mcr.microsoft.com` and downloads its binaries at boot. A network isolated cluster (outbound type `none`, bootstrap artifact source `Cache`) takes them from a private Azure Container Registry instead, which fetches them from Microsoft Artifact Registry through a cache rule; the cluster never asks MCR. Microsoft documents it as generally available, with either an AKS-managed registry or one the cluster's owner brings, Premium, reached through a private endpoint ([Create a network isolated AKS cluster](https://learn.microsoft.com/en-us/azure/aks/network-isolated), read 2026-10-29).
- **A cluster in a network of its own needs roles nobody in CI should hand out.** Its control plane's identity must hold Network Contributor on the subnets AKS runs in, and its kubelet's AcrPull on the registry. Granting a role needs `Microsoft.Authorization/roleAssignments/write`, and an identity that can assign roles can widen its own.

The maintainer approved a third cloud on 2026-10-28, about $20 a month together with an inference reference, and, on 2026-10-29, made a separate Microsoft account for it and signed it up for Azure's Free Trial. The subscription holds nothing but these runs. A trial has a spending limit (nothing is charged to a card while its credit lasts), four vCPUs in a region in all, and no quota increases.

## Decision

The same two phases as on AWS and Google Cloud, the first proven before the second. This record covers the first; the second waits for the maintainer (below).

**Phase 1: the boundary itself.** `aks/` is Terraform for one run, all of it in one resource group, `airgap-<run>`:

- **A network with no way out.** One virtual network with three subnets, the node's, the API server's and the registry's private endpoint, each with default outbound access off. The cluster's outbound type is `none`: AKS makes no load balancer rule, NAT gateway or route out. No public address, NAT gateway, route table, firewall, peering or gateway is declared anywhere in `aks/`, and static check `aks` fails if one is.
- **The security group says it again**: on the node's subnet, egress to anything outside the network's own range and the pods' overlay range is denied.
- **No name lookup out.** A DNS resolver policy on the network refuses every name, the domain `.`, except, in a rule of higher priority, the registry's (`azurecr.io`, whose private zone `privatelink.azurecr.io` answers with the private endpoint's addresses) and the network's own VM names (`internal.cloudapp.net`), which Azure answers and no outside party reads. A rule follows a CNAME chain: a name that ends under an allowed name is let through, and one that passes through a refused one is refused.
- **AKS's own parts from inside.** A network isolated cluster: outbound type `none` and bootstrap artifact source `Cache`, with the run's own registry and the cache rule AKS looks for (`aks-managed-mcr`, `mcr.microsoft.com/*` into `aks-managed-repository/*`). The registry fetches AKS's images and binaries from Microsoft Artifact Registry on the first pull, outside the network, and serves them inside; the node's container runtime asks it instead of MCR.
- **One registry inside, two ways in.** The run's Premium registry is reached by the node through a private endpoint in the network, and from outside by the runner's own address alone (an IP rule, everything else refused), the connected side that copies in what the run carries, by digest. No admin user, no anonymous pull. Premium because a private endpoint and an IP rule need it.
- **An API the operator reaches and nothing else does**: API Server VNet Integration puts the API server's address in a subnet delegated to AKS, which the node reaches inside the network without DNS; the public endpoint answers the runner's own address only (`/32`). No run command (`az aks command invoke`), a way in the authorized ranges do not cover. One node.
- **NetworkPolicies enforced**: Azure CNI in overlay mode with Cilium's dataplane, as kindnet on kind, the VPC CNI on EKS and Dataplane V2 on GKE.
- **No add-on that needs a way out**: no monitoring, no Azure Policy, no Defender. The node OS does not upgrade under a run (channel `None`).

`tests/e2e/aks.sh` runs the boundary checks the AWS and GKE runs run, each refusal beside a control from the same pod and from the node's own network: no TCP to the internet by address; no answer for a public name and no public resolver asked directly, while the registry's name resolves to its private endpoint and the cluster's own services resolve; the registry reachable on 443. And two of its own: neither a pod nor the node opens TCP to `mcr.microsoft.com`, and the registry holds AKS's own images under `aks-managed-repository/`, which says the node started from the cache. The DNS check is shown its violation once, on a run with the resolver policy off the network (`dns_firewall = false`), before it is trusted.

**Who may act, and as what.** No secret exists for any identity here. Set up from the maintainer's own login:

- **Two Entra applications federated to GitHub**, each by one subject: a job of this repository in one environment, in GitHub's immutable form, the owner and the repository by their numeric ids (`repo:heyvaldemar@10498744/kubernetes-air-gapped-ai-agent@1421238353:environment:<env>`; ADR 14). Both environments admit main alone. The creation identity (`azure-validation`) is Contributor on the subscription and may write the runs' states; it cannot assign a role. The sweep identity (`azure-sweeper`) holds one custom role, `airgap-sweeper`: read anything, delete a resource group. A push to any other branch that changes the run runs one job that asks Entra for each identity's token from that branch and passes only when both are refused.
- **Two standing managed identities** (`aks/bootstrap.sh`, in `airgap-identities`): `airgap-cluster`, the control plane's, with Network Contributor on the subscription and Managed Identity Operator on the kubelet's; `airgap-kubelet` with AcrPull on the subscription. A run uses them and grants nothing, so the creation identity never needs a role it could widen its own with.
- **A monthly budget of 10 in the account's currency**, `flagship-monthly`, with alerts at 50%, 80% and 100% of spend and at 100% of the forecast. The account bills in Canadian dollars, so it is CA$10, and every amount Cost Management and the budgets give here is in CA$; list prices are in US dollars.

**The run** (`.github/workflows/aks.yml`): by hand on main, and weekly on Tuesdays at 03:37 UTC behind `AZURE_VALIDATION_ENABLED`, the day no other cloud run of this repository's or the EKS platform's takes. Before anything is billed, it reads the subscription's budgets, and refuses to apply when this month, as Cost Management counts the whole subscription, the standing groups with the runs', leaves no room for one more run under CA$20 (`scripts/aks.sh guard`): a budget only alerts. Until 2026-11-13 the runs alone were held to CA$10; that day the maintainer set CA$20 a month, about US$15, for everything. It then reads the region's vCPU quotas, the subscription's total and the node's family, and refuses a node that does not fit them (`scripts/aks.sh quota`), before the network and the registry are made; the daily sweep prints them. One Terraform state per run in the state account, with Entra auth (the account's shared keys are off). The teardown deletes the run's resource group whatever happened, which takes the cluster and the group AKS makes for the node with it, then looks for anything of this run or any earlier one, by name and by its `run-id` tag, and reports the cost from list prices and from Cost Management. A run first deletes any group an earlier one left. `.github/workflows/aks-sweep.yml` runs daily as the sweep identity and deletes a run's groups once GitHub says that run has finished, or once they are older than three hours; then it prints the budget and what Cost Management has counted for each run this month.

**What the trial allows.** Four vCPUs in the region in all: the boundary's one Standard_D2as_v7 (2 vCPUs, 8 GiB) fits with room for nothing but a second like it. The agent's node, as on GKE, is four vCPUs and 16 GiB: one Standard_D4as_v7 would take the whole quota, with no room for a second node, a surge node or a node pool on the side, and ADR 20's drill needs two. The trial does not offer every size either: in eastus it lists no v5 or v3 D-series, so the run's node is v7. ## Phase 2, the agent

The maintainer decided on 2026-11-13: the agent goes on the subscription, on Pay-As-You-Go, within CA$20 a month for all of it. Phase 2 is what the AWS and GKE runs do, on the same boundary, with `agent: true` (the dispatch's default) or, on the schedule, `AZURE_AGENT_ENABLED`:

- **The node.** One Standard_D4as_v7, four vCPUs and 16 GiB, the size of GKE's agent node (c3d-standard-4) and AWS's (m7i.xlarge). `max_pods` is 110, as on kind and GKE: AKS holds back 20 MB of memory for each pod a node allows, and at overlay's default of 250 that is 4 GiB of the 16.
- **What crosses.** The same signed file as on kind, AWS and GKE (`scripts/bundle.sh`), built on the runner before anything is billed and loaded into the run's registry, which holds nothing of it until then, every image under its original path (`scripts/inside.sh`; INSIDE is the registry's login server). Then Kyverno and the model policies, the model server, the tool side with Vault, and the gateway, all from the registry inside; the kind e2e's checks of what is inside (9, 10 and 11), the boundary's, the evals, Vault's and the game day.
- **Kyverno's identity.** On AWS Kyverno reads ECR as an IAM role of its own through EKS Pod Identity, on GKE as a Google identity of its own through Workload Identity Federation for GKE. AKS's equivalent, Microsoft Entra Workload ID, has the pod exchange its Kubernetes token for an Entra token at login.microsoftonline.com, outside the network, and a way to it is what this boundary refuses. What a pod reaches with no way out is the node's instance metadata service, 169.254.169.254, which hands out the node's managed identity: the kubelet's, `airgap-kubelet`, AcrPull and nothing else. Kyverno's Azure provider asks it for that identity's token when `AZURE_CLIENT_ID` names it and no secret or federated token is set (`scripts/aks.sh kyverno`, the admission controller's environment), and exchanges it at the registry, through the private endpoint, for a registry token. The signatures and AI-BOMs Kyverno reads are in the registry the kubelet pulls from as the same identity.
- **Who else can ask.** Any pod that reaches the metadata service can get that token. The agent's namespace lets nothing out but DNS, the MCP server, the gateway and the model (`manifests/network-policies.yaml`), so it cannot: `tests/e2e/aks.sh` tries from a pod there, beside a pod in a namespace with no NetworkPolicy, which can. The MCP server's and Vault's namespaces deny egress the same way, and the model servers' pods have no egress at all. Kyverno's namespace and `kube-system` can reach it.
- **One resolver.** AKS's documentation says that from Kubernetes 1.37 it turns LocalDNS on by itself on a node pool made while the cluster holds no NetworkPolicy, as every run's is: a DNS proxy on the node, at 169.254.10.10 and .11, which the pods then ask instead of CoreDNS. The agent's NetworkPolicies let DNS out to kube-dns, CoreDNS's pods, alone, on kind, AWS and GKE alike, and GKE's NodeLocal DNSCache is off for the same reason (ADR 22). azurerm has no setting for it, so the run sets the one node pool's LocalDNS to Disabled through the AKS API (`azapi_update_resource.local_dns`, `2025-10-01`), which reimages the node inside the apply; a profile said explicitly is one AKS keeps. `tests/e2e/aks.sh` checks that a pod asks the kube-dns Service. `local_dns: true` sets it to Required instead, on a 4-vCPU node, the smallest AKS allows it on, to show that check its violation. This is the boundary's cluster as much as the agent's, so the boundary-only runs have it too.
- **Vault's volume.** Vault's claim (ADR 24) gets AKS's default class, an Azure disk, which AKS makes in its node group and deletes with the cluster: nothing to release before the delete, where GKE keeps the disk.
- **The schedule.** `AZURE_AGENT_ENABLED` is set only once a run by hand has passed and Cost Management has counted one, and only if four or five such runs a month fit under the CA$20. Cost Management counted 43460974068 on 2026-11-14, read by the sweep [43575116543](https://github.com/heyvaldemar/kubernetes-air-gapped-ai-agent/actions/runs/43575116543): CA$0.36, CA$0.22 of it the node, CA$0.07 the registry, CA$0.06 the network, and under a cent DNS and the disk. Five a month would be about CA$1.80. It counted the whole subscription's November at CA$0.69, all of it seven runs, the four of 2026-11-13 among them (43471274808 CA$0.04, 43475307852 CA$0.03, 43482241992 on the 4-vCPU node CA$0.14). `AZURE_AGENT_ENABLED` was set on 2026-11-14, so the scheduled run takes the agent and the 4-vCPU node from Tuesday 2026-11-17. - Cost Management had nothing for the subscription on its second day: every run on 2026-10-30 was answered "doesn't have valid WebDirect/AIRS offer type", and so was the maintainer's own login. - A pod on AKS can reach the instance metadata service, 169.254.169.254, and ask it for the kubelet identity's token, which may pull from any registry in the subscription and nothing else. Phase 2 reads signatures with it, from Kyverno, and closes it to the agent's namespaces with their NetworkPolicies, which a check tries. AKS can also restrict pods' access to it, which would take it from Kyverno too; the run does not.
- The registry fetches what the cache rule names from Microsoft Artifact Registry, outside the network, when the node first asks for it. That is a way out for the registry, Microsoft's service, not for anything in the network: a workload can ask the registry for a path under MCR, and MCR serves only Microsoft's images. The registry also lets trusted Azure services past its IP rule (the default), which concerns who may reach it, not what leaves.
- Azure's DNS also answers queries for the allowed names, so a workload can put data into a name under `azurecr.io` or `internal.cloudapp.net`; the first is answered by Microsoft, the second inside Azure. On AWS and Google Cloud the allowed names are AWS's and Google's in the same way.
- The control plane identity's Network Contributor and the kubelet's AcrPull are on the whole subscription, because a run's resources do not exist before the run. The subscription holds nothing else, and both identities exist only for these runs.
- A run's resource group, its registry's name and the subscription's id are in the run's public log and the repository's variables. None of them is a credential.
- A budget alerts; it stops nothing. On the trial the spending limit was what stopped spending. The maintainer upgraded the subscription to Pay-As-You-Go on 2026-11-10, which removed it; the portal showed the credit, CA$280.50 of CA$283.31, good until 2026-11-29, and after it the card on file pays. With no spending limit the run makes a second budget, `flagship-ceiling`, CA$20 a month with alerts at CA$10, CA$15 and CA$20 spent and at CA$20 forecast, if it is missing (`scripts/aks.sh ceiling`), and applies nothing until it is there; the guard held the runs to CA$10 a month until 2026-11-13 and holds the whole subscription to CA$20 from then; and the daily sweep deletes what a finished run left. The sweep after the upgrade, [42918164864](https://github.com/heyvaldemar/kubernetes-air-gapped-ai-agent/actions/runs/42918164864), read the spending limit Off, both budgets with their alerts and no other budget in the subscription (the portal's card of a budget on the credit is not one), the month's spend at CA$0.09 for three runs, and nothing of any run left. ## Alternatives

- **The AKS-managed registry.** AKS makes, keeps and deletes it, with its private endpoint, in the node's group; nothing to assign. But its public access is off and the runner could not copy in what the run carries, so a second Premium registry would be needed for that, at the same price a day.
- **A private cluster (Private Link).** The API server would answer inside the network only, and the runner, with no machine of its own in the network, could reach it through `az aks command invoke` alone, which runs a pod in the cluster from an image the cluster must pull: a way in, and no way to run the probes from the runner's own kubectl as on AWS and GKE.
- **Outbound type `block`.** AKS would add its own rules to block egress; it is in preview, and on a network the cluster's owner brings, the documented equivalent is outbound type `none` with a security group, which this is.
- **Azure Firewall with FQDN rules.** About $0.40 to $1.25 an hour before traffic, more than the rest of a run, and it acts on traffic that has a route; here nothing has one.
- **A Private DNS Resolver with forwarding rules.** It forwards names, it does not refuse them, and its endpoints cost about $0.25 an hour each.
- **Roles granted by the run.** The creation identity would need `roleAssignments/write`, conditioned to three roles and to service principals, and could still give them to the sweep identity. Standing identities with their roles given once by the maintainer keep the run from granting anything.
- **A GitHub branch in the subject instead of an environment.** The applications were made with environment subjects on 2026-10-29; an environment also lets GitHub refuse a branch before any job runs, and the branch job here shows Entra refusing it too.

## How to explain this to a customer

In your Azure subscription, the cluster runs in a network with no way out: no public address anywhere, no NAT, and AKS told to make none. AKS normally downloads its own parts from Microsoft's public registry; here it takes them from your own registry inside the network, which fetches them from Microsoft and nothing else. We also close the door most designs leave open: even with no way out, Azure's DNS answers questions about any name on the internet, and data can leave inside those questions. A DNS policy on the network refuses every name but your registry's and the network's own, and a test on a real subscription shows both, that nothing gets out and that it would have, without that policy.

Nothing in it holds a password or a key. The test proves to Azure who it is with a token from GitHub that only this repository's main branch can get, for an identity that can build and tear down this test and grant nothing; a second identity can only delete, and it sweeps up after a run that did not finish. Everything a run makes is in one resource group, so tearing it down is one delete, and the test checks afterwards that nothing is left.
