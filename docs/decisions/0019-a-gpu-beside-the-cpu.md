# 19. A GPU beside the CPU: the same model, the same weights, measured side by side

- Status: accepted, 2026-10-23
- Date: 2026-10-22

## Context

The repository serves its models on CPU (ADR 4) and sizes a server by measurement: on four vCPUs, Granite-4.0-1B answers about 45 of the agent's calls a minute, and parallel slots add nothing, because they split the same cores (README, Sizing). On AWS the same model on an m7i.xlarge answered at half the runner's rate (ADR 18). The question a buyer asks next is what a GPU changes, and at what price per call, inside the same boundary.

The account's quota for G and VT instances was 0. AWS raised it to 8 vCPUs on 2026-10-22 after an appeal that described this test: one g6.xlarge, about an hour a week, under $5 a month, inside the $30 kill-switch.

## Decision

- **The same model, the same weights, the same engine.** The GPU server mounts the CPU server's signed model image by the same digest, verified by the same admission, and runs the CUDA build of the same llama.cpp release (b11429). Only the hardware differs, so the difference measured is the hardware's.
- **Inside the same boundary.** One g6.xlarge (one NVIDIA L4) in the same private subnets, on EKS's AL2023 NVIDIA image, tainted so only what asks for a GPU lands on it. The CUDA image and NVIDIA's device plugin cross in the same signed bundle, pinned to their linux/amd64 manifests (`airgap/images-gpu.txt`), seeded only when a run asks for a GPU.
- **Measured with the agent's own calls.** `scripts/capacity.py` against both servers at concurrency 1, 2, 4 and 8: calls a minute, p50 and p95, output tokens a second, and what a thousand calls cost at each node's list price. The CPU server as the evals run it (one slot, two threads); the GPU server with eight slots, since on a GPU requests in flight are batched.
- **From inside the cluster, for long enough.** A Job beside the servers, in a namespace of its own whose one door into inference is for its pod, on the servers' port, for the minutes it runs (`manifests/gpu/measure.yaml`); closed after and checked closed. Each level lasts at least 30 seconds and starts with one untimed round. The first runs measured from the runner, through a port-forward, six calls a level; see the spread below. The GPU is measured that way once more in each run, beside the runner's time to the EKS API, so the path's share of a call stays on record.
- **Then a larger model on the same GPU.** Granite 4.1 at 8B parameters (Apache-2.0, a 5.0 GiB file), built, signed and attested like the default and carried in the same bundle on GPU runs. Once the first model is measured its server goes, since a pod holds the GPU whole, and the larger one is served, checked on its digest and in the GPU's memory, measured the same way, and run through the evals with everything they read started afresh: the task floor off, as for every model in the matrix, and every other gate on.
- **Checked like everything else** (`scripts/gpu.sh check`): the node offers one GPU; the GPU server runs on it with the CPU server's model digest; the model is in the GPU's memory, by `nvidia-smi` in the server's container; a pod asking for the GPU with weights nobody signed is refused.
- **The GPU node for the minutes it is measured.** The run's first apply makes no GPU node. After the evals, the game day and the CPU server's measurement, a second apply adds it; a third takes it away as soon as it is measured, whatever happened, and the cost table prices it between the two.
- **By hand first** (`gpu: true` on a dispatch), weekly once a run has passed (`AWS_GPU_ENABLED`, on from 2026-10-23).

## When EC2 has no L4, 2026-11-09

The scheduled run of 2026-11-05, [42005832115](https://github.com/heyvaldemar/kubernetes-air-gapped-ai-agent/actions/runs/42005832115), and the dispatch after it, [42036957092](https://github.com/heyvaldemar/kubernetes-air-gapped-ai-agent/actions/runs/42036957092), made no GPU node: EC2 answered `InsufficientInstanceCapacity` for g6.xlarge in us-east-1a, then in us-east-1b, the run's two zones, and EKS gave the node group up after about half an hour each time (`CREATE_FAILED`, `AsgInstanceLaunchFailures`). Everything before the GPU had passed. The run's zones are the first two the region lists (`aws/network.tf`); a third would add six interface endpoints to every run, GPU or not.

The node group now asks for two types, in order (`gpu_instance_types` in `aws/variables.tf`): g6.xlarge, one NVIDIA L4, and g5.xlarge, one NVIDIA A10G, with the same 24 GB of GPU memory, four vCPUs and 16 GiB, at $1.006 an hour against $0.8048 (instances.vantage.sh, 2026-11-09). EKS fills an On-Demand node group by the order of its types, so the A10G is made only when EC2 has no L4 for it. The run reads the type from the node it got, names the card wherever it names a number, `NVIDIA L4 (g6.xlarge)` or `NVIDIA A10G (g5.xlarge), the fallback when EC2 has no L4`, prices that type in the cost table, and fails when the GPU nvidia-smi names is not the one its type carries (`scripts/gpu.sh card`, held by check `aws` and three plants). An A10G's numbers are never put in a row with the L4's, and the README's GPU numbers stay the L4's. A dispatch can ask for the A10G first, `gpu_types: g5.xlarge g6.xlarge`, to prove the fallback; the schedule asks for the L4 first.

That dispatch, from main on 2026-11-09, run [42656218231](https://github.com/heyvaldemar/kubernetes-air-gapped-ai-agent/actions/runs/42656218231): the GPU node was a g5.xlarge, `gpu.sh check` passed with its GPU named `NVIDIA A10G (g5.xlarge), the fallback when EC2 has no L4`, every GPU row of the measurement carries that name, and the cost table priced the node at $1.006 an hour for the 0.49 h it existed, $0.50 of about $1.21 for the run's 1.68 h. The larger model held 15,530 MiB of the A10G's 23,028. 121 of 121 checks in the job passed (`scripts/release-numbers.py 42656218231 vault aws`), the agent's evals at the release gates, and nothing was left behind. This proves the A10G's path from the node to the cost table. It does not show EKS moving to the second type when EC2 has no L4: that is the order EKS gives an On-Demand group's types, and the next run that finds no L4 is the one that shows it.

The scheduled run before, [40845619217](https://github.com/heyvaldemar/kubernetes-air-gapped-ai-agent/actions/runs/40845619217) on 2026-10-29, failed earlier, in the bundle: the 5 GB `granite-4.1-8b` layer broke off with an HTTP/2 `INTERNAL_ERROR` from the staging registry. `scripts/bundle.sh` has tried each copy up to three times since 90a8941. ## When EC2 has no GPU at all, 2026-11-11

The second type left two things open: why a node group in two zones stopped at one of them, and what a run should do when EC2 has neither card.

**What the error said, and what it did not.** Run 42005832115's node group failed with one refusal, for g6.xlarge in us-east-1a, and the text went on: "You can currently get g6.xlarge capacity by not specifying an Availability Zone in your request or choosing us-east-1b, us-east-1c, us-east-1d, us-east-1f." The dispatch three and a half hours later, 42036957092, failed with the same text for us-east-1b, and offered us-east-1a. That list is every other zone that offers the type, not a zone that has one. The Auto Scaling group behind a node group does ask its other zones ("If the attempt fails, however, Amazon EC2 Auto Scaling attempts to launch the instances in another Availability Zone until it succeeds", AWS, [Amazon EC2 Auto Scaling benefits](https://docs.aws.amazon.com/autoscaling/ec2/userguide/auto-scaling-benefits.html)), and EKS's error carries one refusal of however many there were. In the same account on 2026-10-30, CloudTrail held 14 refused g6.xlarge launches in us-east-1a and 18 in us-east-1b for one node group over those two zones ([kubernetes-llm-inference-gateway](https://github.com/heyvaldemar/kubernetes-llm-inference-gateway), its ADR 5). Neither run of 2026-11-05 kept its own attempts: they went with the node group in the third apply. A run keeps them now (`scripts/aws.sh launches`, in the run's artifact) and prints what CloudTrail holds of the eight days before it (`scripts/aws.sh refused`).

**Every zone that offers the card.** With the GPU node the run makes one more private subnet in every other zone of the region that offers each of the node's types (`aws_subnet.gpu`, `aws/network.tf`), and the node group asks in all of them: in us-east-1 the run's own us-east-1a and us-east-1b, then c, d and f. On 2026-10-30 the gateway repository's run [41089439304](https://github.com/heyvaldemar/kubernetes-llm-inference-gateway/actions/runs/41089439304) found neither card in a, b, c, d or f in its first round and an A10G in us-east-1f in its second, a zone this run did not ask in. A subnet costs nothing, and these hold no endpoint: an interface endpoint answers every subnet of its VPC ("This includes traffic from subnets in other Availability Zones", AWS, [Access an AWS service using an interface VPC endpoint](https://docs.aws.amazon.com/vpc/latest/privatelink/privatelink-access-aws-services.html)), so the six stay in two zones, and the note of 2026-11-09 that a third zone would add six was wrong. The GPU subnets use the first private subnet's route table, the VPC's own range and S3's prefix list, give nothing a public address, and exist from the apply that makes the GPU node to the apply that takes it away. AWS's documentation does not say whether the group walks the types within a zone or the zones within a type, so the run claims neither: it names the card it got, the zone it came from and every launch EC2 refused before it, and the first run that is refused shows the order.

**No capacity is said, not failed.** When EC2 has no GPU of either type in any of those zones, EKS gives the node group up after about half an hour and the apply fails. That one failure is no longer the run's. `scripts/aws.sh capacity` reads the node group and its Auto Scaling group from AWS and passes only when all of this holds: EKS gave the node group up (`CREATE_FAILED`); every health issue it names is `AsgInstanceLaunchFailures` with `InsufficientInstanceCapacity`; the Auto Scaling group has launches on record; and every one of them was refused, for capacity. A launch refused for the account's vCPU limit, a launch that was not refused and may be an instance, a node that launched and never joined, an apply that failed with the node group active, a node group that cannot be read: each stays the run's failure, as before. On a miss the run goes on without a GPU. Step `No GPU, EC2 had none to give` writes "GPU: no capacity", with every refusal by zone and type, to the run's summary, as a warning on the run's page, and as the line `GPU node: none, EC2 had no capacity (...)` in the results the status page reads. The GPU steps do not run, the node group and the GPU subnets go in the third apply, and the cost table has no GPU row: run 42005832115's table priced a g6.xlarge that never existed, 0.57 h and $0.46 of its $1.11. Nothing that was checked is passed over: the boundary, the agent's evals, Vault's credential and the game day all ran before the GPU step, and a miss changes none of them. What a miss leaves unmeasured is the GPU, and the README's GPU numbers name the run they came from.

**Two scheduled misses in a row fail.** One week without a GPU is EC2's weather. The second scheduled run in a row that asks for a GPU and is given none fails in that step (`GPU_MISSES_IN_A_ROW: "2"`, `.github/workflows/aws.yml`), so the GPU cannot go unmeasured week after week behind green runs. The count is read from GitHub: the six scheduled runs before this one, and in each what the step that asks for the GPU and the miss step came to (`scripts/ec2-capacity.py streak`). Only a scheduled run that was given a GPU node clears the count. One that asked for no GPU, stopped before it asked, or failed its GPU apply for another reason neither counts nor clears it, since no GPU was measured in it either; a run the rule failed counts, so the week after it fails too. A run by hand says its miss and is not counted. When GitHub does not answer for the list or for any run on it, the run fails rather than pass the rule unread.

**What it costs.** Nothing on a run that gets its GPU: no new resource is billed. A miss costs the wait, about half an hour of the cluster with no GPU node: $0.42 an hour at the run's list prices (the control plane, one m7i.xlarge, six endpoints in two zones), about $0.24.

**A GPU that comes late.** With five zones to ask, a node group is likelier to be given a GPU near the end of its wait than to be given none, and the job had no room for that: run 42656218231, whose GPU came at once, took 112 of the job's 130 minutes and ended 94 minutes into the role's two-hour session, with the third apply and Vault's release at the very end. The job has 170 minutes now, and takes a new session from GitHub's OIDC token before the GPU's part.

**Held by** two static checks. `aws`: the Terraform tests (a GPU subnet in every other zone that offers each type and none where one is missing, no public address, and after an apply against the mocked provider the node group over all five subnets and the GPU subnets on the first private route table), five plants. `gpu`: the workflow's steps (the GPU step survives only the failure `aws.sh capacity` passes, the GPU steps run only on a node that was made, the limit is two, no step's failure is passed over) and `tests/static/aws-gpu-capacity.sh`, twenty cases of `aws.sh capacity`, `missed`, `launches` and `refused` against an AWS and a GitHub made of files, the refusal's text taken from run 42005832115; nineteen plants. All twenty-four caught.

## Consequences

- A g6.xlarge at $0.8048 an hour for the part of the run it exists: the second apply, the device plugin, the server, the checks and the measurement, then the destroy. Weekly, within the $15 a month the maintainer set for GPU work.
- For a model this small at low traffic the CPU node is still the smaller bill, $0.20 an hour against $0.80; the GPU is the cheaper call once there are calls to batch.
- The bundle grows on a GPU run by 2.6 GB for the CUDA image and 5.0 GiB for the larger model, to 11 GB against 6.0 (run 40052214040), and the runner frees disk for it as the kind e2e does. Its signature is over its sha256 (ADR 8): cosign holds a blob it signs in memory at about twice its size, and run 40048612675 was killed signing this one.
- The larger model's weights and its cache take 15,460 MiB of the L4's 23,034; the default model's server goes first, since a pod holds the GPU whole, and the GPU node is up for 0.65 h of a 1.5 h run.
- The device plugin runs in its own namespace at the privileged Pod Security level, which reading the kubelet's device-plugin socket needs; its image is held to what the bundle carried like any other.
- A run EC2 gives no GPU is green, with "GPU: no capacity" on its page and in its results, and has measured nothing on a GPU; the second scheduled one in a row is red. Whoever wants the GPU's numbers reads the run they name, not the latest run.

## Alternatives

- **vLLM on the GPU.** The usual server for GPU serving, and the one the quota appeal named. It reads weights in another format, so the GPU would serve different files from the ones signed and attested for the CPU, and the comparison would measure two engines and two files at once. The CUDA build of the same llama.cpp keeps everything but the hardware equal.
- **A GPU node every week from the start.** The first run by hand says what it costs and what it shows before it becomes a standing line in the account's bill.
- **A capacity reservation before the node group** (2026-11-11), as [kubernetes-llm-inference-gateway](https://github.com/heyvaldemar/kubernetes-llm-inference-gateway) does (its ADR 5). EC2 answers a reservation in seconds, zone by zone, so a run would know in minutes, and could ask every zone for the L4 before any zone for the A10G. A reservation bills as the instance does from the moment it is active, is made outside Terraform and imported, and one a teardown missed bills until its end date; that repository took six billed runs to get it right. Here the GPU is one part of a run whose other parts are done by then, the wait costs about $0.24, and a node group that is given nothing leaves nothing behind. Taken up again if misses, or weeks on the A10G, become the rule.
- **Failing the run on every miss**, as until 2026-11-11. The scheduled run of 2026-11-05 went red with every check of the boundary and the agent passed, for stock EC2 did not have that morning.
- **A second try later in the same run.** Another half hour of the cluster each time, and on 2026-11-05 EC2 was still out three and a half hours later.

## How to explain this to a customer

We run the same signed model on an ordinary server and on one with a GPU, inside the same closed network, and measure both with the requests your agent actually makes: how many answers a minute, how long each takes, and what a thousand of them cost. Then you choose the hardware from numbers, not from a vendor's benchmark. If the cloud has no GPU to rent that hour, the run says so in plain words and still checks everything else: it does not fail for the provider's stock, and it does not pass twice in a row without the measurement.
